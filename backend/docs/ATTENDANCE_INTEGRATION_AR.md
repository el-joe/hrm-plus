# دليل تكامل الحضور — الأجهزة والجوال والتحقق بالوجه

**الإصدار:** 1.0.0 (قيد الإصدار) · **آخر تحديث:** 2026-11-12
**الجمهور:** مسؤولو الحضور، مدير النظام، فريق التشغيل، ومن سيبني محوّل جهاز أو مزوّد وجه حقيقي. المرجع الفني بالإنجليزية: `ATTENDANCE_DEVICES.md` و`FACE_VERIFICATION.md`.

> ## تنبيه حالة التكامل
>
> - **أجهزة البصمة (B3):** لم يزوّد العميل بعد بالشركة المصنّعة والطراز والبرنامج الثابت (Firmware). لذلك **لا يُدعم أي جهاز حقيقي حاليًا**. المتاح: **محوّل محاكاة** للتطوير (موسوم «محاكاة» في كل شاشة وسجل) و**استيراد ملفات CSV / Excel** من برنامج الجهاز — وهو يصلح للتشغيل الفعلي.
> - **التحقق بالوجه (B4):** لم يُختر مزوّد ولا ترخيص بعد. المزوّد الحالي **محاكاة لا يجري أي مطابقة حيوية ولا كشف حيوية**؛ كل نتيجة موسومة `is_simulated: true` و«محاكاة». **لا يجوز استخدامه في الإنتاج.** الافتراضي في السياسات «اختياري».
> - **GPS والتحقق الجغرافي:** مُنفَّذ بالكامل في الخادم ويعمل فعليًا.

## 1. البنية العامة: محرك حضور واحد لكل المصادر

```
جهاز البصمة (إرسال/سحب/ملف) ─┐
تطبيق الجوال (GPS + وجه)      ├─▶ أحداث أولية (attendance_raw_events) ─▶ محرك الحضور ─▶ أيام محسوبة (attendance_days)
الإدخال اليدوي والجماعي       │      لا تُعدَّل أبدًا، مفتاح منع تكرار        حسب السياسة     تأخير، انصراف مبكر، إضافي، غياب
استيراد Excel                 ┘
```

- **مصدر** كل حدث محفوظ: جهاز البصمة، الجوال (GPS)، يدوي، استيراد — ويظهر في كل الشاشات والتقارير (تقرير «مصدر الحضور»).
- **الأحداث الأولية** لا تُعدَّل؛ الخطأ يُلغى (يبقى ظاهرًا) ويُضاف حدث تصحيح.
- **محرك الحضور** يحسب اليوم وفق **نسخة سياسة الحضور** السارية ويحفظ لقطة الحساب ونسخة السياسة. المعالجة تتم عبر طابور المهام فور ورود الحدث، مع إعادة حساب ليلية ومعالجة كل 10 دقائق للأحداث المتأخرة.
- **إقفال الفترات**: أي تغيير على يوم مقفل يُحفظ كتسوية منفصلة وتلتقطه الرواتب كتصحيح.

## 2. أجهزة البصمة: نموذج المحوّلات

لا تستخدم كل الأجهزة البروتوكول نفسه، لذا يتصل النظام بالأجهزة عبر **واجهة محوّل موحّدة** (`AttendanceDeviceAdapter`) لها ثلاث وظائف:

| الوظيفة | الغرض |
|---|---|
| `testConnection` | اختبار الاتصال وقراءة معلومات الجهاز |
| `pull` | سحب السجلات بعد آخر مؤشر (أو ضمن نطاق تاريخي) |
| `parsePush` | ترجمة البيانات التي يرسلها الجهاز أو وسيطه |

كل وسائل النقل (إرسال، سحب، ملف) تمر بالمكوّن نفسه (`DeviceEventIngestor`) الذي: يبني مفتاح منع التكرار، ويربط مستخدم الجهاز بالموظف، ويحفظ غير المربوط دون حذفه، ويرسل الأحداث للمعالجة، ويسجّل عملية المزامنة.

**المحوّلات المسجلة حاليًا** (`config/attendance_devices.php`): `simulated` فقط («جهاز محاكاة (للتطوير)»)، ويدعم الإرسال والسحب والملف. يولّد سجلات معقولة للتطوير، ويمكن تفعيل «محاكاة فشل» لاختبار مسار الأعطال.

## 3. إعداد جهاز في النظام

**القائمة:** تسجيل الحضور ← **أجهزة الحضور** ← **إضافة جهاز** (صلاحية إضافة أجهزة الحضور).

| الحقل | الوصف |
|---|---|
| الاسم والرقم التسلسلي | الرقم التسلسلي يدخل في رابط الإرسال ومفتاح منع التكرار (أحرف وأرقام و`._-`) |
| الفرع | يحدد المنطقة الزمنية الافتراضية ونطاق البيانات |
| المنطقة الزمنية | وقت الجهاز إن اختلف عن الفرع |
| المحوّل | حاليًا «جهاز محاكاة» فقط |
| طريقة الاتصال | إرسال (Push) أو سحب (Pull) |
| فترة السحب | كل كم دقيقة يُسحب الجهاز |
| بيانات الاتصال | عنوان/منفذ/مفاتيح — **تُحفظ مشفرة** ولا تُعرض |

بعد الحفظ: **اختبار الاتصال**، ثم (للإرسال) **رمز إرسال جديد** — يظهر مرة واحدة ويُحفظ كقيمة مجزأة (SHA-256)؛ إصدار رمز جديد يبطل السابق فورًا.

## 4. طرق الاتصال: الإرسال والسحب والملفات

### 4.1 الإرسال (Push)

الجهاز (أو برنامج الشركة المصنّعة أو وسيط صغير) يستدعي:

```
POST /api/v1/devices/{serial}/events
Authorization: Bearer <رمز الإرسال>
Content-Type: application/json

{ "events": [
  { "user_id": "1024", "time": "2026-11-10 08:01:22", "direction": "in", "log_id": "88123", "verify_mode": "fingerprint" },
  { "user_id": "1024", "time": "2026-11-10T16:59:02+02:00", "direction": "out" }
] }
```

- `time` بلا فرق توقيت = وقت الجهاز (منطقته الزمنية، وإلا منطقة الفرع).
- `direction`: `in` أو `out` أو بدونه (يرتب المحرك البصمات بالترتيب).
- حد أقصى 500 حدث في الطلب، و120 طلبًا في الدقيقة لكل جهاز (قابلة للضبط).
- الرد: `received`، `created`، `duplicates`، `unmatched`، `sync_log_id`، `simulated`. الأخطاء: `401 device_unauthorised` (رمز خاطئ)، `403 device_inactive` (جهاز معطّل)، `422 invalid_payload` (يُسجَّل كإرسال فاشل).

### 4.2 السحب (Pull)

المهمة المجدولة `attendance:sync-devices` تعمل كل 5 دقائق وتسحب الأجهزة التي حان دورها من آخر مؤشر محفوظ. وعند الطلب: **مزامنة الآن**، و**استيراد نطاق تاريخي** (حتى 62 يومًا). المؤشر لا يتقدم إلا عند النجاح، فلا تضيع سجلات.

### 4.3 الملفات (CSV / Excel) — البديل المعتمد حاليًا

**الجهاز ← استيراد سجل الجهاز**:

| العمود | إلزامي | الصيغة |
|---|---|---|
| `device_user_id` | نعم | معرّف المستخدم على الجهاز |
| `time` | نعم | `YYYY-MM-DD HH:MM[:SS]` بوقت الجهاز، أو ISO-8601 مع فرق التوقيت |
| `direction` | لا | `in` / `out` / فارغ |
| `log_id` | لا | رقم السجل في الجهاز |

حتى 20,000 صف. **معاينة** أولًا: جديد، مستخدم غير مربوط، مستلم سابقًا، مكرر في الملف، غير صالح (وقت لا يُقرأ، وقت مستقبلي...). لا يُكتب شيء قبل **استيراد**.

إضافة لذلك، يتوفر **استيراد الحضور** العام (الحضور والانصراف ← الدفعات والاستيراد) لإدخال أيام أو أوقات حضور بالموظف بدل معرّف الجهاز.

## 5. ربط مستخدمي الجهاز بالموظفين

كل جهاز يعرف المستخدمين برقم تسجيل خاص به. **ربط مستخدمي الجهاز**:

- اربط كل معرّف بموظف، **لهذا الجهاز** أو **لجميع الأجهزة** (إن كانت أرقام التسجيل موحدة).
- المعرّفات المجهولة التي أرسلها الجهاز تظهر أولًا مع **أحداث منتظرة**؛ بمجرد الربط تُعالج أحداثها.
- **إزالة الربط** لا تغيّر الأحداث المرتبطة سابقًا.
- من **الأحداث الأولية** يمكن ربط حدث واحد بـ **اربط بموظف…** مع **تذكّر لمستخدم الجهاز هذا**.

الحدث غير المربوط **لا يُحذف أبدًا**؛ يبقى بحالة «غير مربوط» حتى يُعالج.

## 6. المزامنة والأعطال والصحة

- **سجل المزامنة** لكل جهاز: نوع العملية، الوقت، المستلم/الجديد/المكرر/غير المربوط، والرسالة.
- عند فشل السحب: تزيد الإخفاقات المتتالية، وتُحدَّد المحاولة التالية بتراجع متزايد: `min(5 × 2^(n−1), 360)` دقيقة. يظهر في صفحة الجهاز «المحاولة التالية».
- **الحالة الصحية:**

| الحالة | المعنى |
|---|---|
| معطّل | الجهاز غير نشط؛ يُرفض الإرسال ويتوقف السحب |
| فاشل | 3 إخفاقات متتالية أو أكثر |
| يحتاج انتباهًا | فشل حديث، أو لا اتصال منذ أكثر من «مدة انقطاع الجهاز» (افتراضيًا 24 ساعة — الإعدادات ← الحضور) |
| لا يوجد اتصال بعد | لم يتصل منذ إضافته |
| سليم | يعمل طبيعيًا |

- رسائل الأخطاء الظاهرة للمستخدمين لا تتضمن بيانات الاتصال.
- تقرير **مزامنة الأجهزة** في تقارير الحضور ومركز التقارير.

## 7. منع التكرار

- لكل حدث جهاز مفتاح فريد: `device:{الرقم التسلسلي}:{معرّف المستخدم}:{الوقت بالثانية}`، بقيد فريد في قاعدة البيانات. السجل نفسه الوارد مرتين (إعادة سحب، إرسال + ملف، دفعة مُعادة) يُحتسب «مكررًا» ولا يُنشئ حضورًا.
- محاولات الجوال لها معرّف طلب فريد (`request_uuid`): إعادة الإرسال بعد انقطاع الشبكة لا تكرر البصمة.
- يوم الحضور فريد لكل موظف + تاريخ + وردية.
- الإدخال اليدوي الجماعي لا يحل محل حضور فعلي مسجل من جهاز أو جوال.

## 8. إضافة محوّل لجهاز حقيقي

**الشروط المسبقة:** تأكيد الشركة المصنّعة والطراز والبرنامج الثابت من العميل (B3)، ووثائق الـ SDK أو البروتوكول، و**جهاز فعلي للاختبار**.

الخطوات (للمطور):

1. إنشاء صنف محوّل يطبّق `AttendanceDeviceAdapter` في `app/Services/Attendance/Devices/Adapters/`: `testConnection()`، و`pull()` (يعيد بصمات بتوقيت UTC والمؤشر التالي، ويرمي استثناء برسالة آمنة عند الخطأ)، و`parsePush()` إن كان الجهاز يرسل.
2. تسجيله في `config/attendance_devices.php` مع `'simulated' => false` وطرق الاتصال، وإضافة تسميته في `lang/{ar,en}/devices.php`.
3. اختبارات آلية ببيانات مسجلة من الجهاز الحقيقي: منع التكرار، المناطق الزمنية، الاتجاه، مسار الفشل.
4. اختبار ميداني: انحراف الساعة، انقطاع الكهرباء، امتلاء ذاكرة السجلات، إعادة تسجيل المستخدمين.
5. بعد ذلك فقط يُذكر الطراز «مدعومًا» في وثائق العميل.

أمثلة لبروتوكولات قد تُصادف (أمثلة فقط — **لا شيء منها منفذ أو مدعوم حاليًا**): بروتوكول ADMS / Push لأجهزة ZKTeco أو الـ SDK الخاص بها، واجهة BioStar 2 من Suprema، واجهة ISAPI من Hikvision، Anviz CrossChex. كل منها يحتاج محوّلًا واختبارًا خاصًا.

## 9. الحضور عبر الجوال وGPS

### 9.1 المسار

1. يطلب التطبيق `GET /api/v1/me/attendance/today`: القواعد، والمواقع المسموحة، ووضع الوجه.
2. يطلب إذن الموقع بعد شرح السبب، ويحدد الموقع (مهلة 20 ثانية) ويرسل الدقة ومؤشر الموقع الوهمي (أندرويد).
3. ينفذ التحقق بالوجه إن لزم.
4. يرسل `POST me/attendance/check-in|check-out` مع `request_uuid` والإحداثيات والدقة ووقت الهاتف ومعرّف الجهاز والإصدار.
5. **الخادم يعيد التحقق من كل شيء** ولا يثق في حكم الهاتف.

### 9.2 قواعد التحقق في الخادم

| الفحص | القاعدة | الإعداد الافتراضي |
|---|---|---|
| التسجيل عبر الجوال مسموح | في نسخة سياسة الموظف | — |
| موقع مسموح محدد | قاعدة الموظف ← قاعدة قسمه ← مواقع فرعه | — |
| المسافة | المسافة (هافرساين) ≤ نصف قطر الموقع + هامش الدقة | نصف القطر 150 م، الهامش 20 م |
| دقة GPS | الدقة المُبلغة ≤ الحد | 50 م |
| نافذة الوردية | ضمن نافذة الحضور/الانصراف لوردية اليوم | حسب الوردية |
| فرق ساعة الهاتف | الفرق عن وقت الخادم ≤ الحد | 300 ثانية |
| موقع وهمي | مؤشر الموقع الوهمي من الهاتف | — |
| محاولات متكررة | عدد المحاولات المرفوضة في الساعة | 3 |
| الوجه | حسب الوضع (متوقف/اختياري/مطلوب) وعدد المحاولات | 3 محاولات |

القيم الافتراضية في **الإعدادات ← الحضور**، وتُضبط لكل **نسخة سياسة حضور** (الورديات والجداول ← سياسات الحضور)، فيمكن أن تختلف لكل فرع أو قسم أو مجموعة أو موظف.

### 9.3 مواقع الحضور ونطاقها

- **الفروع ← الفرع ← مواقع الحضور**: الإحداثيات ونصف القطر (نطاق دائري؛ النطاقات المضلعة غير مبنية).
- **مواقع العمل للجوال**: قواعد لموظف أو قسم (مع الفرعية): موقع محدد أو **أي مكان (عمل عن بُعد)** مع فترة سريان. «أي مكان» يلغي فحص المسافة فقط؛ تبقى فحوص الدقة والوقت والوردية والموقع الوهمي والوجه.

### 9.4 النتائج

| رمز الاستجابة | المعنى | ما يراه الموظف |
|---|---|---|
| 201 | سُجّل الحضور/الانصراف | تم تسجيل الحضور — النجاح الوحيد |
| 202 | مشبوه — أُحيل للمراجعة (مثل موقع وهمي، فرق ساعة، فشل وجه في الوضع الاختياري، غير مسجل الوجه مع سياسة «إرسال للمراجعة») | أُرسل للمراجعة، لم يُسجَّل بعد |
| 422 `attendance_rejected` | مرفوض مع الأسباب (خارج الموقع، دقة منخفضة، خارج نافذة الوردية، التسجيل عبر الجوال غير مفعّل، لا يوجد موقع محدد...) | لم يتم التسجيل + السبب والمسافة والمحاولات المتبقية للوجه |

**لا يُعتمد أي تسجيل مشبوه بصمت.** كل المحاولات (المقبولة والمرفوضة) محفوظة للتدقيق، والمشبوهة تنتظر في **مراجعة تسجيلات الجوال والويب**؛ الاعتماد يسجل البصمة بوقت حدوثها، والرفض يتجاهلها، وكلاهما في سجل التدقيق. لا يمكن لمراجع أن يقرر في محاولته. المحاولات المعلقة تظهر كتنبيه في حساب الرواتب ولا تُحتسب حضورًا.

**لا يوجد تسجيل بدون اتصال**: التطبيق لا يخزّن محاولات لإرسالها لاحقًا (افتراض A6).

## 10. التسجيل من بوابة الويب

**المسار:** بطاقة **«تسجيل الحضور / الانصراف»** في **الرئيسية** للبوابة وفي أعلى **حضوري** (الجزء `employee/_check-in` مع `resources/js/pages/check-in.js`). ترسل البطاقة `POST /portal/attendance/check-in` أو `check-out` بجلسة البوابة، وتمر المحاولة بالخدمة نفسها التي يستخدمها تطبيق الجوال (`MobileCheckIn`) — **مسار واحد للقناتين**، فالمدخلات نفسها تعطي القرار نفسه.

**الإعداد في نسخة سياسة الحضور** (قسم «تسجيل الحضور من بوابة الويب»):

| الإعداد | الافتراضي | الأثر |
|---|---|---|
| «السماح بتسجيل الحضور من بوابة الويب» | مفعّل (ومعطّل في السياسات التي كان تسجيل الجوال فيها معطّلًا عند الترقية) | عند التعطيل لا يظهر زر التسجيل وتُرفض المحاولة بسبب «تسجيل الحضور من بوابة الويب غير مفعّل لك.» |
| «يجب أن يكون تسجيل الويب داخل النطاق الجغرافي» | مفعّل | مفعّل: فحص الدقة والنطاق الجغرافي كالتطبيق. معطّل: يُسجَّل الموقع فقط (إن توفر) دون فحصه، وتظهر شارة «يُسجَّل الموقع فقط» |

**الفحوص (على الخادم، كالجوال):** التوظيف في التاريخ، تفعيل القناة، النطاق الجغرافي ودقة الموقع (مع هامش الانصراف `checkout_extra_meters`)، نافذة الوردية (رفض أو مراجعة حسب السياسة)، فرق الساعة بين المتصفح والخادم (مراجعة)، المحاولات المرفوضة المتكررة خلال الساعة (مراجعة)، والتحقق بالوجه بكاميرا الجهاز (معطّل / اختياري / مطلوب، مع عدد المحاولات، ثم رفض أو إحالة لمراجعة الموارد البشرية حسب `face_failure_action`). وقت البصمة هو **وقت الخادم** دائمًا.

**فروق المتصفح:** المتصفح لا يستطيع الإبلاغ عن **فحص الحيوية** ولا عن **الموقع الوهمي**، فلا تُرسل هذه القيم من الويب. ويُفحص دقة الموقع في المتصفح **قبل الإرسال** («دقة موقعك ± X م فقط، والحد المقبول Y م…»)، ثم يعيد الخادم الفحص.

**ما يراه الموظف:**

- الأزرار: «تسجيل الحضور» / «تسجيل الانصراف»، وبعد الفشل «حاول مجددًا».
- الشارات: «يُتحقق من الموقع» / «يُسجَّل الموقع فقط» / «أي موقع»، «الدقة ± X م»، «النافذة مفتوحة حتى HH:MM» / «تفتح النافذة الساعة HH:MM» / «لا توجد نافذة وردية الآن»، «بدون تحقق بالوجه» / «الوجه اختياري» / «الوجه مطلوب»، «الوجه غير مسجّل»، «المحاولات المتبقية للوجه: N».
- نافذة الكاميرا: «التحقق بالوجه»، «التقاط الصورة»، «المتابعة بدون الوجه»، «إلغاء».
- النتائج: «تم تسجيل الحضور.» / «تم تسجيل الانصراف.» (201)، «أُحيلت للمراجعة. لن تُسجّل حتى تعتمدها الموارد البشرية.» (202)، أو الرفض مع السبب (422) مثل «أنت على بُعد X م من {الموقع} (المسموح: R م).».
- أخطاء المتصفح والشبكة: «لا يعمل الموقع والكاميرا إلا عبر اتصال آمن (HTTPS)…»، «الوصول إلى الموقع محظور…»، «فشل الاتصال. حاول مجددًا — ستُستكمل المحاولة نفسها ولن تُحتسب مرتين.» (يُعاد استخدام `request_uuid` نفسه، فلا تُحتسب البصمة مرتين).

**التخزين والعرض للإدارة:**

- تُحفظ المحاولة في جدول المحاولات نفسه مع عمود القناة (`channel`: `mobile` / `web`)، وتظهر المشبوهة في **مراجعة تسجيلات الجوال والويب** مع عمود ومرشح **القناة**: «بوابة الويب» / «تطبيق الجوال».
- المحاولة المقبولة تُسجَّل حدثًا أوليًا بمصدر `web_portal`، ويظهر في شاشات الحضور والتقارير بالاسم **«بوابة الويب (GPS)»** (مفتاح منع التكرار `web:{request uuid}`).

**المتطلبات:**

- **HTTPS** (أو `localhost` أثناء التطوير): لا تسمح المتصفحات بالموقع والكاميرا على اتصال غير آمن (انظر DEPLOYMENT_GUIDE_AR.md، القسم 6).
- ترويسة `Permissions-Policy` تسمح بـ `camera` و`geolocation` لصفحات `/portal` فقط (من النطاق نفسه)، وتمنعهما في بقية النظام.
- دقة الموقع في أجهزة الحاسب المكتبية (بلا GPS) غالبًا ضعيفة، فقد تُرفض حسب حد السياسة؛ عطّل «يجب أن يكون تسجيل الويب داخل النطاق الجغرافي» للعاملين عن بُعد إن كان ذلك مقبولًا.

## 11. التحقق بالوجه

### 11.1 طبقة التجريد

| المكوّن | الدور |
|---|---|
| `FaceVerificationProvider` (`enrol`, `verify`, `delete`) | واجهة المزوّد الموحدة |
| `config/face_verification.php` | سجل المزوّدين؛ المزوّد النشط من **الإعدادات ← التحقق بالوجه** |
| `SimulatedFaceProvider` | **محاكاة**: الرمز المرسل من التطبيق يحدد النتيجة (`sim-no-match`، `sim-liveness-fail`، `sim-error`، وغير ذلك = مطابق). لا مطابقة حقيقية |
| `FaceEnrolmentService` | الموافقة، التسجيل، الحذف، الاحتفاظ |
| `FaceVerifier` | التحقق عند التسجيل، قواعد إعادة المحاولة |
| `BiometricStore` | قرص خاص `biometric_files` بمحتوى مشفر بمفتاح التطبيق |

النظام **لا يقارن الصور بنفسه**؛ المطابقة وكشف الحيوية (مكافحة الانتحال) مسؤولية مزوّد معتمد (على خوادمه أو SDK معتمد على الجهاز).

### 11.2 قواعد السياسة

في **نسخة سياسة الحضور**:

| القاعدة | المعنى |
|---|---|
| التحقق بالوجه: متوقف / اختياري / مطلوب | متوقف: لا يُطلب. اختياري: يُتحقق إن أرسل التطبيق صورة، والفشل لا يُقبل بصمت. مطلوب: عينة وجه لكل تسجيل |
| محاولات الوجه لكل يوم واتجاه | الإخفاقات المسموحة قبل المسار البديل |
| عند الفشل النهائي | **إرسال للمراجعة** (تعتمد الموارد البشرية أو ترفض) أو **رفض** (يتواصل الموظف مع الموارد البشرية). غير المسجلين يتبعون القاعدة نفسها |

### 11.3 تسلسل الموظف

1. **الموافقة** على معالجة بيانات الوجه (`POST me/face/consent` بإصدار نص الموافقة الحالي). تغيير الإصدار في الإعدادات يطلب الموافقة من الجميع مجددًا. التسجيل مرفوض بلا موافقة.
2. **التسجيل** (`POST me/face/enrol`).
3. **التحقق** عند كل تسجيل حضور/انصراف (`face` ضمن طلب التسجيل). الرموز: 422 `face_required` / `face_retry` (مع المحاولات المتبقية)، 202 `face_failed` / `face_not_enrolled` (مراجعة).

### 11.4 ربط مزوّد حقيقي

1. اختيار مزوّد بـ SDK للجوال يوفر كشف الحيوية/مكافحة الانتحال، والحصول على الترخيص وبيانات الاعتماد (B4).
2. وضع بيانات الاعتماد في `.env` و`config/services.php` (لا في قاعدة البيانات ولا السجلات).
3. تطبيق `FaceVerificationProvider`: `enrol()` ينشئ الشخص لدى المزوّد ويعيد معرّفه؛ `verify()` يتحقق من جلسة/رمز SDK في الخادم ويعيد النتيجة والدرجة والحيوية؛ `delete()` يحذف الشخص لدى المزوّد.
4. تسجيله في `config/face_verification.php` (`'simulated' => false`) وفي خيارات الإعداد وتسميته باللغتين.
5. في التطبيق: دمج SDK المزوّد وإرسال رمزه في `face.token`.
6. تبديل الإعداد، وإعادة تسجيل الموظفين، وإجراء **تقييم أثر لحماية البيانات (DPIA)** قبل التشغيل.

## 12. الخصوصية والاحتفاظ والحذف

- **لا صور خام ولا قوالب حيوية بنص صريح:** مرجع المزوّد مشفر في قاعدة البيانات؛ أي ملف (صورة تسجيل إن فُعّل الاحتفاظ بها، أو قالب يعيده المزوّد) مشفر على قرص خاص لا يُقدَّم عبر الويب. صور التسجيل **لا تُحفظ** افتراضيًا («الاحتفاظ بصورة تسجيل مشفرة» متوقف).
- جداول النتائج (`face_verifications`) تحفظ النتيجة والدرجة والوقت فقط.
- **سحب الموافقة** (`DELETE me/face/consent`) يحذف البيانات الحيوية فورًا: لدى المزوّد، والملفات المشفرة، والمرجع؛ يبقى سجل بالتواريخ والسبب فقط.
- **إنهاء الخدمة** يحذف البيانات عند سريانه.
- **الحذف المجدول** `face:purge` يوميًا 02:15: التسجيلات الأقدم من «إعادة التسجيل بعد» (افتراضيًا 730 يومًا)، وتسجيلات المنتهية خدمتهم، ونتائج التحقق الأقدم من «الاحتفاظ بنتائج التحقق» (افتراضيًا 365 يومًا).
- **الوصول:** شاشة **تسجيلات الوجه** تعرض حالة الموافقة والتسجيل فقط، وكل عرض يُسجَّل؛ **حذف البيانات الحيوية** لموظف بصلاحية مستقلة مع سبب إلزامي، ومسجَّل في التدقيق.
- محاسب الرواتب وأي دور بلا صلاحية التحقق بالوجه لا يصل لهذه البيانات.
- بيانات الموقع: تُحفظ الإحداثيات والدقة مع كل محاولة لأغراض التدقيق والمراجعة؛ التطبيق لا يتتبع الموقع في الخلفية.

## 13. مسارات بديلة عند التعذر

| الحالة | المسار البديل |
|---|---|
| الجهاز لا يتصل | استيراد ملف سجل الجهاز (CSV/Excel) — لا تكرار بفضل مفتاح منع التكرار |
| موظف بلا جهاز أو جوال | الحضور الجماعي أو التصحيح الفردي (مصدر «يدوي» مميز) |
| فشل الوجه أو عدم التسجيل | حسب السياسة: إحالة لمراجعة الموارد البشرية، أو الرفض والتواصل مع الموارد البشرية لتصحيح يدوي |
| موظف لا يستطيع استخدام التحقق بالوجه لسبب مشروع | ضبط سياسته (موظف/مجموعة) على «متوقف» أو «اختياري»، مع الإبقاء على فحوص GPS |
| عمل ميداني/عن بعد | قاعدة «أي مكان (عمل عن بُعد)» للموظف أو القسم |
| موظف نسي البصمة | طلب تصحيح من البوابة أو التطبيق |

## 14. حل المشكلات

| المشكلة | السبب المحتمل والحل |
|---|---|
| `401 device_unauthorised` | رمز الإرسال خاطئ أو أُصدر رمز جديد؛ انسخ الرمز الجديد إلى الجهاز/الوسيط |
| `403 device_inactive` | الجهاز معطّل؛ **تفعيل** |
| `422 invalid_payload` | صيغة JSON غير صحيحة؛ راجع الصيغة في 4.1 و**سجل المزامنة** |
| أوقات منحرفة بساعات | المنطقة الزمنية للجهاز أو الفرع خاطئة؛ أو أوقات بلا فرق توقيت من جهاز بمنطقة مختلفة |
| أحداث «غير مربوطة» | اربط معرّف المستخدم بالموظف (القسم 5) |
| كثير من «المكرر» | طبيعي عند إعادة السحب أو إعادة الإرسال؛ لا ينشئ حضورًا مزدوجًا |
| الجهاز «فاشل» | راجع رسالة سجل المزامنة، **اختبار الاتصال**؛ الشبكة/الجدار الناري/بيانات الاتصال |
| الأيام لا تتحدث | تأكد أن عامل الطابور `queue:work` والمجدول `schedule:run` يعملان |
| رفض «خارج الموقع» والموظف في الموقع | إحداثيات الموقع أو نصف القطر خاطئان؛ أو دقة ضعيفة داخل المبنى — زد الهامش في السياسة |
| رفض «دقة منخفضة» | في الأماكن المغلقة؛ ارفع حد الدقة في السياسة بحذر |
| رفض «خارج نافذة الوردية» | الموظف بلا وردية ذلك اليوم أو خارج النافذة؛ راجع **تقويم الجداول** |
| «ساعة الهاتف تختلف» | الهاتف بوقت يدوي؛ فعّل الوقت التلقائي |
| «لم يتم تحديد موقع حضور لك» | لا مواقع نشطة لفرعه ولا قاعدة له |
| «التحقق بالوجه مطلوب» والموظف غير مسجل | يوافق ويسجل وجهه من التطبيق أولًا |
